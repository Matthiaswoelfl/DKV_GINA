Persönliches Finanz-Dashboard

Planung: Rückfragen, Architektur, Datenmodell, Ordnerstruktur, Phasen. Stand 17.11.2026

Rückfragen

  1. Bank: Im Auftrag steht noch der Platzhalter. Welche Bank ist es? Eine anonymisierte Beispiel-CSV mit 3–5 Zeilen, inklusive Kopfzeilen, wäre ideal. Daraus baue ich ein passendes Preset (Spaltenzuordnung, Encoding, Vorzeichenlogik). Ohne Angabe: generisches Mapping plus DKB-Preset.
  2. Konten: Nur ein Girokonto oder mehrere (Giro, Kreditkarte, Tagesgeld)? Bei mehreren käme ein Feld Konto dazu, damit Umbuchungen die Zahlen nicht verfälschen.
  3. Sparen und Umbuchungen: Als Ausgabe zählen oder als eigener Typ „Umbuchung"? Vorschlag: Eine Kategorie kann als „Umbuchung/Sparen" markiert werden und wird separat ausgewiesen.
  4. Datenhaltung: Empfehlung IndexedDB mit Dexie: kein Backend, ein einziger Befehl, Daten bleiben im Browser. Nachteil: Die Daten hängen am Browserprofil, das JSON-Backup gleicht das aus. Alternative SQLite mit Express: eine Datei auf der Platte, aber mehr Wartung. Ist dir „Datei auf der Platte" wichtig?
  5. Wiederkehrende Zahlungen: Nur monatliche oder auch quartalsweise und jährliche (z. B. Versicherungen)? Vorschlag: alle drei erkennen und auf den Monat umrechnen.

Architektur

  • Stack: React 18, TypeScript (strict), Vite, Tailwind, Recharts, Dexie, Vitest, ESLint, Prettier.
  • Routing: react-router mit Dashboard, Transaktionen, Import, Kategorien und Regeln, Budgets, Einstellungen (Daten und Backup).
  • Schichten: domain/ (reine Logik, keine DB, kein React, vollständig testbar), db/ (Dexie-Schema, Repositories), ui/ (Seiten, Komponenten, Charts).
  • Formatierung: Zentrale format.ts über Intl: 1.234,56 € und TT.MM.JJJJ. Beträge intern als Cent-Integer.
  • Datenfluss: useLiveQuery für reaktive Listen, Aggregationen im Speicher (für private Datenmengen schnell genug).
  • Privatsphäre: Keine externen Requests, keine CDN-Fonts, keine Analytics.
  • Seed: npm run seed oder Button „Beispieldaten laden": ca. 6 Monate Fake-Buchungen mit festem Zufalls-Seed, als Seed markiert und wieder löschbar.

Datenmodell

Beträge als amountCents (Integer, Ausgaben negativ). Daten als ISO-String YYYY-MM-DD.

TabelleFelder
transactionsid, date, amountCents, type (income/expense), categoryId?, counterparty, description, note?, accountId, importHash?, source (manual/csv/seed), createdAt
categoriesid, name, kind (income/expense/transfer), color, sortOrder, archived
rulesid, field (counterparty/description/both), match (contains/startsWith/regex), pattern, categoryId, priority, enabled
budgetsid, categoryId, monthlyCents, optional validFrom
accountsid, name, bank?
importProfilesid, name, encoding, delimiter, headerRowIndex, columnMap, signConvention, dateFormat
settingskey, value (Theme, letzter Export, Standardzeitraum)

Duplikaterkennung

importHash = hash(accountId + date + amountCents + normalisierter Empfänger + Verwendungszweck + Vorkommensindex). Der Vorkommensindex wird innerhalb einer Datei hochgezählt, damit zwei identische Buchungen am selben Tag nicht als Duplikat gelten. Ein erneuter Import derselben Datei liefert dieselben Hashes und überspringt alles.

Regeln

Auswertung nach Priorität, erste Übereinstimmung gewinnt. Manuell gesetzte Kategorien werden nie überschrieben. Beim manuellen Kategorisieren erscheint der Vorschlag „Regel für ‚REWE' erstellen?".

Umsetzung in Phasen

Nach jeder Phase laufen Tests, Linter und tsc. Danach folgt eine Zusammenfassung mit Testanleitung.

  1. Phase 1Setup, Schema, Transaktions-CRUD, Liste mit Suche, Filtern, Sortierung.
  2. Phase 2Kategorien, Regeln, CSV-Import (Mapping, Vorschau, Duplikate), Seed.
  3. Phase 3Dashboard: Zeitraum, KPIs mit Vormonatsvergleich, Kategorie-Chart mit Klickfilter, 12-Monats-Verlauf, Kategorie-Trend, Top-Empfänger.
  4. Phase 4Budgets, wiederkehrende Zahlungen, CSV- und JSON-Export, Restore.
  5. Phase 5Dark Mode, Leerzustände, Fehlermeldungen, Tablet-Layout, README.
